## Executive Summary

**No regression of the serving.** The static file work that landed with #49 shows up exactly where it was aimed: viriatum went from **losing** to nginx on small and mid files to **beating** it, the ratio moving from 0.62x to 1.39x and from 0.63x to 1.48x, with the processor cost of a thousand requests more than halved on both. Nothing else moved beyond the noise of the machine, and the noise was substantial: **nginx, whose binary did not change, was down a median of 14.8%** across the ten comparable workloads, so any absolute figure from this run has to be read through that.

Four ratios of the twenty five that are readable lost more than a tenth. Two are the proxy workload, which the evidence puts on the machine rather than on the proxying, and two are the interfaces against uvicorn, which are not comparable at all because the interpreter changed underneath them. Neither pair is a regression of the serving, and both are set out below.

Two things this run turned up are about the measuring rather than the serving. The baseline's cost figures for the proxy and for the three interface workloads are **wrong**, and were wrong when they were recorded: the proxy row summed the proxy and its upstream because both are the same binary, and the interface rows recorded zero because the process they run under never matched the pattern. Both were fixed in #52, so this run measures them correctly for the first time and the stored ones cannot be compared against. Separately, the run **aborted at workload 15** because the package no longer imports on the interpreter the harness reaches for by default.

**The machine was not quiet.** Load stood at 4.00 over 18 cores with a virtual machine of the container daemon and an editor running. The size of that is measurable, because three of the five servers did not change between the two runs:

nginx is the honest measure of the run's noise floor, and it is about **-15%**. Against that, viriatum's own median of -3.1% is a gain rather than a loss. This is the reason the sections below are read by ratio and not by throughput.

## 2. Static File Serving

The headline result. The cache that holds served files open, which landed through #53 and #52, moved the small and mid workloads from a loss against nginx to a win.

| Workload             | Against | Baseline | This run | Change      |
| -------------------- | ------- | -------: | -------: | ----------: |
| `static-small-alive` | nginx   |    0.62x |    1.39x | **+122.5%** |
| `static-small-alive` | caddy   |    0.89x |    1.65x | **+84.8%**  |
| `static-mid-alive`   | nginx   |    0.63x |    1.48x | **+135.9%** |
| `static-mid-alive`   | caddy   |    1.06x |    2.21x | **+107.9%** |
| `static-large-alive` | nginx   |    1.33x |    1.69x | +27.7%      |
| `static-large-alive` | caddy   |    1.13x |    1.02x | -9.7%       |
| `static-large-close` | nginx   |    1.13x |    1.24x | +10.1%      |
| `static-large-close` | caddy   |    1.14x |    1.15x | +0.5%       |

In absolute terms the subject went from 55,437 to 96,752 requests a second on the small file and from 50,553 to 101,085 on the mid one, which is a doubling on a run where everything else got slower.

The single negative, `static-large-alive` against caddy at -9.7%, sits below the threshold and beside a +27.7% against nginx in the very same workload, so it reads as caddy's own variance rather than as a loss. The large file is dominated by the writing of the payload rather than by the opening of it, which is the part the cache changed, so no movement there was expected either way.

## 4. Proxying

The one domain where a ratio crossed the threshold, and the evidence says the machine rather than the proxy path.

| Server     |  Baseline |  This run |  Change | Ratio change |
| ---------- | --------: | --------: | ------: | -----------: |
| `viriatum` |    94,307 |    79,335 |  -15.9% |            - |
| `haproxy`  |   124,198 |   118,690 |   -4.4% |       -12.0% |
| `nginx`    |   115,686 |   100,004 |  -13.6% |        -2.7% |
| `pingora`  |    84,705 |    78,862 |   -6.9% |        -9.6% |
| `caddy`    |     4,837 |     5,256 |   +8.7% |       -22.6% |

Two of the four ratios lost more than a tenth. Read against the rest of the run, both look like the machine: the ratio against nginx, the closest comparable proxy, moved -2.7%, and against pingora -9.6%. The -22.6% against caddy is arithmetic rather than substance, caddy proxies at 5,256 requests a second against viriatum's 79,335 and any movement in so small a denominator swings a 19x ratio hard, and caddy was the one server that got faster in a run where everything else slowed.

Worth re-measuring on a quiet machine before it is dismissed, which is F-04.

## 5. Python Interfaces

The subject got faster in absolute terms on all three, and the ratios still fell, because the interpreter changed underneath the comparison.

| Workload                   | Subject base | Subject now | Change | Ratio base | Ratio now | Ratio change |
| -------------------------- | -----------: | ----------: | -----: | ---------: | --------: | -----------: |
| `python-wsgi-alive`        |      109,909 |     126,148 | +14.8% |     30.97x |    31.38x |        +1.3% |
| `python-asgi-alive`        |       68,546 |      88,976 | +29.8% |      1.93x |     1.60x |       -17.0% |
| `python-asgi-stream-alive` |       25,702 |      29,046 | +13.0% |      1.05x |     0.76x |       -27.6% |

The baseline drove these on Python 3.9 with gunicorn 23.0.0 and uvicorn 0.39.0. This run could not, for the reason in F-01, and drove them on Python 3.13 with gunicorn 26.2.0 and uvicorn 0.52.4. Both sides of the ratio moved, and uvicorn moved further than viriatum did, so the falling ratio says uvicorn 0.52 on 3.13 is faster than uvicorn 0.39 on 3.9 and says nothing at all about the serving of the tree.

**These three ratios are not evidence of anything** until a baseline exists that was recorded on the same interpreter. The absolute column is the only readable part, and it is up on all three.

## 6. Cost

Processor time per thousand requests fell on every workload that is comparable, and by more than half on the two the cache touched.

| Workload             | CPU base | CPU now | RSS base | RSS now |
| -------------------- | -------: | ------: | -------: | ------: |
| `static-small-alive` |     24.0 |    10.0 |     54.2 |    73.8 |
| `static-mid-alive`   |     26.3 |     9.8 |     50.2 |    73.0 |
| `static-large-alive` |    139.2 |   111.8 |     51.7 |    48.4 |
| `default-alive`      |      6.9 |     5.9 |     88.2 |    88.8 |
| `listing-template`   |    277.5 |   214.0 |     57.2 |    57.2 |
| `error-plain`        |     12.3 |     9.2 |     68.5 |    67.7 |

Memory rose about 20 MB on the two cached workloads, from roughly 54 to 74 MB and 50 to 73 MB. That is the cache holding files open and is the price of the throughput above, paid deliberately. It is flat everywhere the cache is not involved.

The proxy and interface rows are deliberately absent from that table. Their baseline figures are not figures, see F-02.
